#+title: gnosisd

~gnosisd~ is Gnosis' canonical knowledge and learning server. It owns Org
documents, parsed nodes and links, themata, review state, FSRS scheduling,
SQLite persistence, blobs, backups, and synchronization.

Ordinary clients use authenticated typed HTTP ~/v1~. They never open the
canonical database or calculate scheduling. The Unix socket is reserved for
local operators: device bootstrap/revocation, backup, recovery, repair, and
diagnostics.

* Build and run

#+begin_src sh
nix develop
cargo run --bin gnosisd -- \
  --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  --database "$HOME/.local/share/gnosis/gnosis.sqlite" \
  --blob-root "$HOME/.local/share/gnosis/blobs" \
  --http-listen 127.0.0.1:7842
#+end_src

HTTP binds to loopback. Tailscale Serve may provide Tailnet HTTPS. Do not expose
the Unix socket or database.

~GET /health~ returns ~{"status":"ready"}~ only after a store round trip.
Unavailable storage returns HTTP 503. OpenAPI 3.1 is public at
~GET /v1/openapi.json~.

* Local operator control

~gnosisd-admin~ speaks bounded Unix protocol v1. Success output is JSON. Device
tokens are returned once; SQLite stores only SHA-256 digests.

#+begin_src sh
gnosisd-admin --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" system-info
gnosisd-admin --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  device-create emacs --scope read --scope review --scope content:write
gnosisd-admin --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" device-list
gnosisd-admin --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  device-revoke DEVICE_ID
gnosisd-admin --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  admin repair --batch-size 100
#+end_src

Ordinary document, thema, review, asset, and synchronization work does not use
the Unix socket.

* HTTP contract

Every data route requires a device bearer token with exact ~read~, ~review~,
~content:write~, ~settings:write~, or ~admin~ scopes. CORS is disabled. Request
bodies, responses, queues, parsing work, and connection counts are bounded.
Mutations are not automatically retried.

The API retains:

- document create/replace/rename/tombstone, exact revisions, digests, and blobs;
- node search/catalog, byte spans, title paths, and inbound/outbound links;
- thema search/catalog, lifecycle, concepts, and direct review suspension;
- online review sessions, concealed pending questions, grading, desired-state
  operations, immutable events, and progress;
- device-bound snapshots, deltas, cursors, SSE wakeups, staged blobs, and
  sequenced offline content/asset/review reconciliation;
- explicit offline review-pack acquisition, asset verification, and retained
  results;
- revisioned settings, dashboard projections, health, and OpenAPI.

Public IDs are opaque strings. Existing updates use ~If-Match~. Durable
mutations use device-scoped ~Idempotency-Key~ or typed operation IDs. Exact
retries return retained results. Stale revisions, conflicts, and unknown
delivery remain explicit.

Managed assets use ~assets/<sha256>/<name>~. The server verifies path, digest,
size, media type, and active state before canonical publication.

* Ownership and storage

One daemon-owned thread holds the canonical SQLite connection. Reads and atomic
writes pass through bounded queues. Accepted writes finish after client
disconnect. No transaction or blocking guard crosses an async suspension point.
SQLite files use mode ~0600~.

Server schema v3 stores documents, nodes, links, themata, scheduling, review
history, sessions, attempts, devices, settings, snapshots, feed revisions,
offline operations, retained results, and conflicts. Public IDs never expose
SQLite row IDs.

Documents and assets use immutable SHA-256 blobs outside SQLite. Accepted Org
revisions parse and index in the same transaction that moves the document head.
Invalid Org cannot change canonical state. Removed nodes remain queryable as
inactive historical nodes.

The functional domain contains no SQLite, Tokio, JSON, socket, filesystem,
orgize, clock, or randomness types.

* Backups and recovery

Online backup runs through the database owner and includes a consistent SQLite
snapshot, every referenced blob, and a SHA-256 manifest.

#+begin_src sh
gnosisd-admin --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  admin backup create --directory "$HOME/.local/share/gnosis/backups"
gnosisd-admin --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  admin backup verify BACKUP_PATH
gnosisd-admin --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  admin backup prune --directory "$HOME/.local/share/gnosis/backups" --keep 2
gnosisd-admin --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  admin backup restore-validate BACKUP_PATH \
  --temporary-directory "$HOME/.local/share/gnosis/restore-check"
#+end_src

Restore validation materializes a temporary instance without replacing live
state. Cold restore requires stopped daemon:

#+begin_src sh
systemctl --user stop gnosisd
install -d -m 0700 "$XDG_RUNTIME_DIR/gnosis"
gnosisd --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  --database "$HOME/.local/share/gnosis/gnosis.sqlite" \
  --blob-root "$HOME/.local/share/gnosis/blobs" \
  --restore-from BACKUP_PATH
systemctl --user start gnosisd
#+end_src

Cold restore validates and stages the complete backup before replacement. It
refuses running-daemon/startup-lock races and preserves prior targets plus
SQLite sidecars under the reported mode-0700 rollback directory.

* Deployment

Systemd user units and Pi runbook live under ~deployment/~ and
~docs/raspberry-pi.org~. The service keeps HTTP on loopback and grants writes
only to Gnosis state/runtime paths.
