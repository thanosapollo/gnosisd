#+title: Gnosis Core

Gnosis Core is the source of truth for Gnosis knowledge and learning data.  It
serves the ~gnosis~ Emacs frontend, command-line, and future clients through a
versioned local protocol.  The Emacs package keeps its established UI and is
not a separate product named emacs-gnosis.

* Ownership and trust boundary

~gnosisd~ is the only process that opens the database. Every client, including
the ~gnosis~ diagnostic program, uses the socket protocol and never sends SQL.
The daemon is local-only and single-user. It creates its socket with mode
~0600~ and enforces mode ~0600~ on SQLite. The protocol does not provide
authentication and must not be exposed as a remote transport.

One dedicated thread owns the only SQLite connection. Reads and writes pass
through one bounded queue, and every projection replacement is one short
transaction. A stale expected revision fails before any rows change. The Tokio
tasks that serve sockets never own a connection, transaction, or database lock.

The default bounds are:

- 1 MiB request and response frames;
- 128-byte request IDs;
- 32 simultaneous connections;
- one in-flight request per connection;
- eight queued database operations.

* Running the daemon and client

Enter the pinned development environment for Rust, Cargo, rustfmt, Clippy, and
rust-analyzer:

#+begin_src sh
nix develop
#+end_src

Build the release package without entering the development shell:

#+begin_src sh
nix build
#+end_src

Start the daemon with explicit local paths:

#+begin_src sh
cargo run --bin gnosisd -- \
  --socket "$XDG_RUNTIME_DIR/gnosis.sock" \
  --database "$HOME/.local/share/gnosis/gnosis.sqlite"
#+end_src

Exercise protocol version 1 through the diagnostic client:

#+begin_src sh
cargo run --bin gnosis -- --socket "$XDG_RUNTIME_DIR/gnosis.sock" system-info
printf '#+TITLE: Example\n' | cargo run --bin gnosis -- \
  --socket "$XDG_RUNTIME_DIR/gnosis.sock" import-org example
cargo run --bin gnosis -- \
  --socket "$XDG_RUNTIME_DIR/gnosis.sock" get-document example
gnosis --socket "$XDG_RUNTIME_DIR/gnosis.sock" legacy-info
gnosis --socket "$XDG_RUNTIME_DIR/gnosis.sock" due-themata 20260714 --limit 20
gnosis --socket "$XDG_RUNTIME_DIR/gnosis.sock" get-thema THEMA_ID
#+end_src

Use ~--if-revision N~ with ~import-org~ for conflict detection. Omitting it
allows an unconditional create or replacement. Identical content is an
idempotent no-op and keeps its revision.

* Protocol

Each message is a four-byte big-endian length followed by a UTF-8 JSON object.
Every request carries protocol version ~1~, an opaque request ID, and one typed
method:

- ~system.info~
- ~document.import~
- ~document.get~
- ~legacy.info~
- ~thema.get~
- ~review.due~

The application protocol exposes opaque string document and node IDs. SQLite
row identifiers, SQL, paths, dependency errors, and backtraces never enter a
response. Stable error codes distinguish malformed requests, unsupported
versions, invalid documents, missing documents, revision conflicts, overload,
and internal failure.

* Domain and Org projection

The domain has no SQLite, async runtime, JSON, socket, filesystem, or orgize
types. ~LinkOccurrence~ records ordered textual occurrences and half-open UTF-8
byte ranges. ~NodeEdge~ records the unique semantic source-to-target relation.
~ThemaConcept~ separately records a learning association as ~Primary~,
~Supporting~, or ~Reference~.

The parser preserves the selected live Gnosis compatibility contract for file
and heading IDs, inherited tags, indexed ancestors, hierarchical title paths,
link ownership, unresolved targets, and the SHA-1 compatibility digest. New
content identity uses SHA-256. Run the shared-semantic parity checks with:

#+begin_src sh
tools/check-org-parity.sh tests/fixtures/org/basic.org
tools/check-org-parity.sh tests/fixtures/org/no-file-id.org
tools/check-org-parity.sh tests/fixtures/org/duplicate-links.org
tools/check-org-parity.sh tests/fixtures/org/unicode.org
tools/check-org-parity.sh tests/fixtures/org/compatibility.org
#+end_src

Two checked-domain corrections are deliberate. The current Elisp aggregate
function errors on an unowned top-level link when no file ID exists; Rust
ignores that unowned link. Current Elisp also emits an ID-bearing heading with a
blank title; Rust rejects it. Byte spans and SHA-256 are Rust-only fields.

* Database and backups

The database path is supplied to ~gnosisd~.  The deployed Gnosis instance uses
=~/.local/share/gnosis/gnosis.sqlite= with its socket at
=${XDG_RUNTIME_DIR}/gnosis/gnosis.sock=.
Foreign keys and strict tables protect projections, link occurrences, semantic
edges, themata, and thema-to-concept associations. Stop the daemon cleanly
with SIGINT or SIGTERM before copying the database for backup. Online backup
and restore commands are not part of this slice. Startup uses an atomic
~SOCKET.startup-lock~ directory while checking and replacing a stale socket. If
a process is killed during that short startup window, inspect and remove the
abandoned lock directory before restarting.

** Legacy Emacs snapshot

Close Emacs before taking the final migration snapshot, then create a fresh
daemon database without changing the source database:

#+begin_src sh
gnosisd \
  --database "$HOME/.local/share/gnosis/gnosis.sqlite" \
  --migrate-legacy "$HOME/.config/emacs/gnosis/gnosis.db"
#+end_src

The offline migration accepts schema-v9 databases, refuses an existing target
or active Emacs lease, and publishes only after SQLite integrity, foreign-key,
and row-count checks pass. All legacy tables and rows are preserved. The
conflicting legacy ~node_tag~ table is stored as ~legacy_node_tag~ while the new
document projection schema is added alongside it.

The daemon exposes the imported snapshot read-only. ~legacy-info~ reports its
source and row counts, ~due-themata~ returns a bounded deterministic queue, and
~get-thema~ returns one thema with its extras, tags, links, and complete review
state.  The Emacs frontend calls these methods through ~gnosis-core.el~ without
changing its established buffers or keymaps.  Review answers remain on the
legacy compatibility path until the daemon exposes one atomic review command.

* Current exclusions

This foundation does not yet write legacy scheduling or review history, expose
TCP, add authentication or TLS, discover or watch files, support Markdown,
compute embeddings, or synchronize multiple daemons.
