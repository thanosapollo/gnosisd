#+title: Gnosis Core

Gnosis Core is the source of truth for Gnosis knowledge and learning data. It
serves the ~gnosis~ Emacs frontend, command-line, and future clients through a
local administration protocol and an authenticated HTTP API.

* Ownership and trust boundary

~gnosisd~ is the only process that opens the database. Clients use the Unix
socket or HTTP API and never send SQL. The daemon is single-user and creates
its socket and SQLite database with mode ~0600~. HTTP binds only to loopback by default. Remote access belongs behind a
trusted authenticated proxy or private network boundary.

Every ~/v1~ data endpoint requires a per-device bearer token. Tokens carry
~read~, ~review~, ~content:write~, ~settings:write~, or ~admin~ scopes. Secrets
are returned once and SQLite stores only their SHA-256 digests. Device and
backup administration remains local-socket-only.

One dedicated thread owns the SQLite connection. Reads and writes pass through
one bounded queue. No transaction, blocking guard, or connection crosses an
async suspension point. Accepted writes complete even if the client leaves.

The default bounds are:

- 1 MiB frames and HTTP request bodies;
- 128-byte request IDs;
- 32 simultaneous Unix connections;
- eight queued database operations;
- 64 concurrent HTTP requests with 30-second timeouts.

* Build and run

#+begin_src sh
nix develop
cargo run --bin gnosisd -- \
  --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  --database "$HOME/.local/share/gnosis/gnosis.sqlite" \
  --blob-root "$HOME/.local/share/gnosis/blobs" \
  --http-listen 127.0.0.1:7842
#+end_src

The diagnostic client uses protocol version 1:

#+begin_src sh
gnosis --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" system-info
gnosis --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" legacy-info
gnosis --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  device-create phone --scope read --scope review
#+end_src

The Unix message format is a four-byte big-endian length followed by UTF-8
JSON. It provides local diagnostics, legacy read compatibility, online review
sessions and attempts, bounded managed-asset reads, device token
administration, and online backup commands. Stable errors never expose SQL,
paths, dependency failures, or backtraces.

* HTTP API

The ~/v1~ API provides:

- device-bound replica state, resumable snapshots, exact revision deltas, and
  immutable blob downloads;
- optimistic thema create, search, update, archive, and unarchive;
- revisioned Org documents, renames, tombstones, and historical retrieval;
- content-addressed managed assets;
- durable change cursors and cursor-only SSE announcements;
- node search and paged inbound and outbound graph links;
- revisioned canonical review settings;
- one active resumable review session with a persisted ordered queue;
- captured attempts, grading, override, suspension, and idempotent atomic
  commit;
- bounded offline review packs and immutable review reconciliation;
- sequenced offline document, lifecycle, and asset-create operations.

Mutations use ~If-Match~. A stale revision returns ~412~ with the current
revision and leaves server state unchanged. The first attempt response hides
the answer. Grading returns the detected result, revealed answer, matcher
version, and proposed transition.

The checked OpenAPI 3.1 document is available at ~/v1/openapi.json~. CORS is
disabled. Keep ~gnosisd~ on loopback and terminate HTTPS at a trusted network
boundary.

* Storage

Schema v9 stores native themata, tags, node associations, scheduling state,
exact review history, sessions, attempts, devices, settings, documents, and
the node graph. It also stores replica snapshots and feed revisions, review
packs, immutable offline operations and results, device sequence state, and
conflict evidence. Public IDs are opaque text. Imported numeric thema IDs are
retained and new resources use UUIDv7.

Org documents and assets use immutable SHA-256 blobs outside SQLite. SQLite
tracks logical paths, heads, revisions, renames, tombstones, and the monotonic
change cursor. Paths are relative and case-unique. Only Org files and supported
files below ~assets/<sha256>/<original-name>~ enter the canonical tree.

Accepted Org revisions are parsed and indexed in the same transaction that
moves the document head. Invalid Org cannot change the head or node graph.
Removed nodes remain queryable as inactive historical nodes.

The domain layer contains no SQLite, Tokio, JSON, socket, filesystem, orgize,
clock, or randomness types. Textual link occurrences, unique semantic graph
edges, and thema-to-node learning associations remain distinct.

* Legacy cutover

Close the legacy Emacs database before the final snapshot. Import schema v9
and the Notes tree into new staging targets:

#+begin_src sh
DATA_DIR="$HOME/.local/share/gnosis"
LEGACY_DB=/path/to/legacy/gnosis.db
NOTES_ROOT=/path/to/notes
gnosisd \
  --database "$DATA_DIR/gnosis.sqlite" \
  --blob-root "$DATA_DIR/blobs" \
  --notes-root "$NOTES_ROOT" \
  --migrate-legacy "$LEGACY_DB"
#+end_src

The importer refuses existing targets, active Emacs leases, symlinks, path
escapes, unsupported files, case collisions, malformed Org, and malformed
legacy values. It reads the source without modifying or embedding it, records
its SHA-256 and mtime, validates table counts, integrity, and foreign keys, then
publishes through a recoverable protocol with the database as the final commit
point.

In-tree assets are normalized into the shared asset model and managed Org and
thema references are rewritten. External URLs remain external. Local links
outside the imported Notes root are rejected.

* Reviews and settings

Matcher version 1 preserves current case, whitespace, quote, and Levenshtein
behavior for basic and cloze themata. Multiple-choice variants require one
exact captured choice. Scheduler version 1 is a pure Rust transition with
captured server time, timezone, day boundary, resolved tag rules, and replayable
interval fuzz.

Canonical timezone, day boundary, and tag rules are revisioned settings.
Existing sessions keep their captured settings when canonical settings change.

* Offline replicas

An offline-capable client owns a real local SQLite replica. It contains
downloaded projections and blobs, a durable server-bound cursor, installed
review packs, and immutable review, content, and asset outboxes. A snapshot is
staged page by page and becomes active only when its terminal page is complete.
If a cursor expires or names a different server history, the client installs a
new snapshot without deleting pending work or conflict evidence. SSE only
wakes the client; correctness comes from pulling the durable delta feed.

Review packs materialize one ordered session and capture every presentation,
thema digest, scheduling revision, scheduler and matcher version, timezone, day
boundary, resolved parameters, and required managed asset. One exclusive
server lease prevents another device or online session from advancing that
materialized session. A disconnected or abandoned client leaves the lease
visible until it is explicitly recovered or abandoned; the daemon never
chooses a winner by timestamp.

Each offline answer is committed locally with its attempt ID and the next
device sequence before the UI advances. Reconciliation verifies the captured
content and base scheduling revision, recomputes the transition from the
recorded versioned inputs, and atomically commits the event, scheduling state,
session progress, suspension, and totals. Exact retries return the retained
result. Stale attempts remain explicit conflicts and cannot change canonical
scheduling state.

Review, document, and asset operations share one contiguous per-device
sequence. Document mutations retain submitted Org or captured lifecycle bases;
invalid and stale revisions remain queryable without replacing the active head
or node index. Tombstones flow through the replica feed and prevent deleted
content from reappearing. Assets are SHA-256 addressed and deduplicated. An
offline asset blob is uploaded and verified before its sequenced create
operation, and dependent Org revisions remain behind it in the outbox.

* Backups

Online backup runs through the database owner and includes a consistent SQLite
snapshot, every referenced blob, and a SHA-256 manifest:

#+begin_src sh
gnosis --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  admin backup create --directory "$HOME/.local/share/gnosis/backups"
gnosis --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  admin backup verify BACKUP_PATH
gnosis --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  admin backup prune --directory "$HOME/.local/share/gnosis/backups" --keep 14
gnosis --socket "$XDG_RUNTIME_DIR/gnosis/gnosis.sock" \
  admin backup restore-validate BACKUP_PATH \
  --temporary-directory "$HOME/.local/share/gnosis/restore-check"
#+end_src

Restore validation materializes and checks a temporary instance without
replacing the live server.

* Scope

This remains a single-user canonical server. multi-server synchronization, Markdown, embeddings, client filesystem
watching, Emacs client migration, and mobile development remain out of scope.

Service installation and migration are covered in
